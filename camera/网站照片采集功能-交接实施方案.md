# 智慧井盖网站“照片采集”功能交接实施方案

> 本文可直接交给现有网站项目的开发者或代码代理执行。接手方应先检查项目技术栈和已有约定，再在现有架构内实现，不应另起一套独立网站。

> 职责说明：本文只用于交接另一个网站项目。ESP32-S3-CAM 固件在独立的 `camera` 项目中开发；网站项目只需实现并稳定提供本文约定的设备 API、存储和登录后展示页面。

## 一、任务目标

在现有智慧井盖网站的登录后管理界面中新增“照片采集”模块，为 ESP32-S3-CAM（OV2640）提供照片上传入口。

完整业务流程：

1. ESP32-S3-CAM 连接用户电脑的 2.4 GHz Wi-Fi 热点。
2. 用户按下设备物理按键。
3. 设备连续采集 3～5 张 JPEG 照片。
4. 设备通过 HTTPS 将照片逐张上传到网站后端。
5. 后端将原图保存到腾讯云 CloudBase 云存储，将批次和照片信息保存到数据库。
6. 登录用户进入“照片采集”页面，查看采集批次、缩略图、原图及上传状态。

本次交接优先实施网站端。ESP32 固件可随后按照本文接口联调。

## 二、接手方执行原则

- 复用项目已有前端框架、组件库、路由、鉴权、请求封装、后端结构和代码风格。
- 不修改现有登录流程，不破坏已有页面和接口。
- 新页面必须保持现有后台的视觉风格、响应式行为和权限规则。
- 图片二进制存入云存储，数据库只保存元数据和文件标识。
- 设备端接口与管理端接口分离；ESP32 不使用管理员登录令牌。
- 所有新增配置使用环境变量，不在源码中提交密钥。
- 若现有项目命名与本文不同，可以按项目约定重命名，但字段含义和功能必须保留。

## 四、页面实施要求

### 4.1 路由与导航

- 建议路由：`/photo-collection`。
- 放在登录后主导航中，名称为“照片采集”。
- 复用现有登录守卫；未登录访问应跳转到登录页或返回现有的未授权页面。

### 4.2 页面布局

页面至少包括以下区域：

1. 统计卡片：今日批次数、今日照片数、失败批次数、最近在线设备数。
2. 筛选栏：设备编号、采集开始时间、采集结束时间、批次状态、查询、重置。
3. 批次表格：批次编号、设备编号、请求张数、成功张数、失败张数、状态、采集时间、完成时间、操作。
4. 分页：复用项目现有分页方式。
5. 批次详情：使用项目现有抽屉、弹窗或详情页组件。
6. 图片宫格：显示序号、缩略图、采集时间、文件大小和上传状态；点击可预览原图。

状态显示：

| 状态值 | 中文显示 | 建议颜色 |
|---|---|---|
| `created` | 等待上传 | 灰/蓝 |
| `uploading` | 上传中 | 蓝 |
| `completed` | 已完成 | 绿 |
| `partial_failed` | 部分失败 | 橙 |
| `failed` | 上传失败 | 红 |

页面必须有加载中、无数据、请求失败和图片加载失败状态。

## 五、数据模型

以下为逻辑模型；接手方可映射到项目已有数据库规范。

### 5.1 `devices`

| 字段 | 类型 | 说明 |
|---|---|---|
| `deviceId` | string | 唯一设备编号 |
| `name` | string | 显示名称 |
| `enabled` | boolean | 是否允许上传 |
| `secretHash` | string | 设备密钥的安全存储形式 |
| `lastSeenAt` | datetime | 最近请求时间 |
| `firmwareVersion` | string | 固件版本 |
| `createdAt` | datetime | 创建时间 |
| `updatedAt` | datetime | 更新时间 |

### 5.2 `photo_batches`

| 字段 | 类型 | 说明 |
|---|---|---|
| `batchId` | string | 服务端生成的唯一批次编号 |
| `deviceId` | string | 设备编号 |
| `requestedCount` | integer | 3～5 |
| `successCount` | integer | 成功上传数量 |
| `failedCount` | integer | 失败数量 |
| `status` | enum/string | 批次状态 |
| `capturedAt` | datetime | 设备报告的采集开始时间 |
| `completedAt` | datetime/null | 完成时间 |
| `createdAt` | datetime | 服务端创建时间 |

### 5.3 `photos`

| 字段 | 类型 | 说明 |
|---|---|---|
| `photoId` | string | 唯一照片编号 |
| `batchId` | string | 所属批次 |
| `deviceId` | string | 设备编号 |
| `sequence` | integer | 批次内序号，从 1 开始 |
| `storageFileId` | string | CloudBase 文件 ID 或对象键 |
| `mimeType` | string | 固定为 `image/jpeg` |
| `sizeBytes` | integer | 文件大小 |
| `width` | integer/null | 图片宽度 |
| `height` | integer/null | 图片高度 |
| `sha256` | string/null | 文件摘要 |
| `capturedAt` | datetime | 拍摄时间 |
| `createdAt` | datetime | 服务端入库时间 |

约束：

- `devices.deviceId` 唯一。
- `photo_batches.batchId` 唯一。
- `photos.photoId` 唯一。
- `photos(batchId, sequence)` 建立唯一索引，保证上传重试幂等。
- 批次的 `deviceId` 必须与鉴权设备一致。

## 六、设备接口契约

统一前缀建议为 `/api/device/v1`。所有响应使用 JSON；成功返回 2xx，参数错误返回 400，鉴权失败返回 401/403，资源不存在返回 404，重复但可安全接受的请求返回原资源或 200。

### 6.1 通用请求头

```http
X-Device-Id: cam-001
X-Timestamp: 1760000000
X-Nonce: random-string
X-Signature: lowercase-hex-hmac-sha256
```

签名原文建议固定为：

```text
METHOD\nPATH\nTIMESTAMP\nNONCE\nSHA256_BODY
```

签名算法：`HMAC-SHA256(deviceSecret, canonicalString)`。服务端校验设备是否启用、签名是否正确、时间戳是否在允许窗口内、Nonce 是否已使用。

开发阶段若先采用简单 Bearer 设备令牌，也必须保持设备令牌与管理员令牌分离，并在接口文档中说明后续替换计划。

### 6.2 创建设备采集批次

```http
POST /api/device/v1/photo-batches
Content-Type: application/json
```

```json
{
  "requestedCount": 3,
  "capturedAt": "2026-09-15T10:30:00+08:00",
  "firmwareVersion": "0.1.0"
}
```

响应：

```json
{
  "batchId": "pb_20260915_xxxxxxxx",
  "status": "created",
  "maxPhotoBytes": 1048576
}
```

服务端必须校验 `requestedCount` 在 3～5 之间。

### 6.3 上传单张照片

为减少 ESP32 实现复杂度，MVP 可使用 `multipart/form-data`：

```http
POST /api/device/v1/photo-batches/{batchId}/photos
Content-Type: multipart/form-data
```

表单字段：

- `sequence`：1～5。
- `capturedAt`：ISO 8601 时间。
- `photo`：JPEG 二进制。

响应：

```json
{
  "photoId": "ph_xxxxxxxx",
  "batchId": "pb_20260915_xxxxxxxx",
  "sequence": 1,
  "status": "uploaded"
}
```

若 `(batchId, sequence)` 已存在，返回已有照片结果，不重复写入对象和数据库。

若 CloudBase 云函数存在请求大小或超时限制，则采用“两步直传”：后端返回短时上传凭证/签名地址，设备直传对象存储，再调用确认接口。接手方必须根据当前 CloudBase 环境限制做出选择并记录结论。

### 6.4 完成批次

```http
POST /api/device/v1/photo-batches/{batchId}/complete
Content-Type: application/json
```

```json
{
  "attemptedCount": 3
}
```

服务端根据实际已入库照片数计算 `successCount` 和 `failedCount`，不得完全信任设备上报值。

响应：

```json
{
  "batchId": "pb_20260915_xxxxxxxx",
  "requestedCount": 3,
  "successCount": 3,
  "failedCount": 0,
  "status": "completed"
}
```

### 6.5 心跳（建议完成）

```http
POST /api/device/v1/heartbeat
Content-Type: application/json
```

```json
{
  "firmwareVersion": "0.1.0",
  "rssi": -55,
  "localIp": "192.168.137.20"
}
```

## 八、上传限制与安全基线

- 仅接受 JPEG，校验扩展名、MIME 和文件头，不能只相信客户端 MIME。
- 单张上限建议 1 MiB，并通过环境变量配置。
- 单批仅允许 3～5 张。
- 设备接口必须使用 HTTPS。
- 正式固件必须校验证书，不允许长期使用 `setInsecure()`。
- 设备密钥不能出现在前端构建产物、日志、接口响应或 Git 仓库中。
- 管理端照片查询必须经过登录鉴权。
- 云存储文件默认私有，以短时 URL 提供预览。
- 上传文件名由服务端生成，不能直接使用客户端路径。
- 记录设备编号、批次、请求结果和错误原因，但日志不记录密钥和完整签名。
- 对设备接口做频率限制、时间戳窗口校验和防重放处理。

建议对象键：

```text
photo-collection/{deviceId}/{yyyy}/{MM}/{dd}/{batchId}/{sequence}.jpg
```

## 九、本地模拟上传脚本

接手方需提供一个可运行的脚本，例如：

```text
scripts/test-device-upload.*
```

脚本职责：

1. 从环境变量读取 API 地址、测试设备编号和设备密钥。
2. 创建一个 3 张照片的批次。
3. 上传项目测试夹具中的 3 张 JPEG。
4. 调用完成接口。
5. 输出 `batchId`、每张结果和最终批次状态。
6. 任一步失败时返回非零退出码。

不得把真实设备密钥写进脚本。

## 十四、ESP32 后续对接约定

ESP32 固件按“拍一张、传一张、释放帧缓冲”的方式运行，避免同时保存 5 张导致内存压力。

- 图片：OV2640 JPEG，首版使用 VGA 640×480。
- 默认拍摄：3 张；允许配置为 3～5 张。
- 默认间隔：500 ms。
- 上传：逐张 HTTPS 请求，每张最多重试 3 次。
- 幂等：同一批次的同一 `sequence` 重试使用相同值。
- 时间：联网后 NTP 校时；服务端记录接收时间作为兜底。
- 按键 GPIO 必须根据具体 ESP32-S3-CAM 板卡原理图选择，避免与摄像头、PSRAM、Flash、USB/JTAG 冲突。
- 电脑热点必须使用 2.4 GHz 并共享互联网。
